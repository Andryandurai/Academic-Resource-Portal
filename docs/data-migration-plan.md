rows total (19 + 152 + 910 + 2 + 11 = 1,094; excluding the auto-generated
and session tables below).

**Tables to deliberately exclude from migration:**
- `auth_permission`, `django_content_type` — regenerated automatically by
  `migrate` on any fresh database; migrating them risks a primary-key clash
  with what Supabase already generated for itself in Phase 2.
- `django_migrations` — already correct on Supabase (all 35 applied there
  directly).
- `token_blacklist_outstandingtoken` / `token_blacklist_blacklistedtoken` —
  JWT session bookkeeping tied to tokens already issued against the *local*
  `SECRET_KEY` and *local* user IDs. Migrating these would either be inert
  (tokens signed with a different secret in production) or actively
  confusing (referencing local-only session history). Every user simply
  logs in fresh against Supabase.
- `auth_group`, `auth_group_permissions`, `accounts_user_groups`,
  `accounts_user_user_permissions` — empty; this app doesn't use Django's
  group/permission system (`accounts.User.role` is the only authorization
  field actually read anywhere in the codebase).

## Relationships

The dependency chain that governs migration order:

```
Department (19)
    │  FK: Semester.department
    ▼
Semester (152)
    │  FK: Subject.semester
    ▼
Subject (910)
    │  FK: Resource.subject
    ▼
Resource (11)
```

Plus one cross-cutting reference: `Resource.uploaded_by` → `User` (all 11
local resources were uploaded by the same local user, id `1`, the local
admin).

Constraints that matter for migration correctness (all already enforced by
the existing migrations — Django will keep enforcing them, this is not new
work, just what a migration script must respect):

- `academics.Semester`: `UniqueConstraint(department, semester_number)`.
- `academics.Subject`: `UniqueConstraint(semester, course_code)` where
  `course_code` is not null (electives may share `NULL`).
- `resources.Resource`: `CheckConstraint` — exactly one of `file`/`url` is
  set, matching `kind`.
- No many-to-many relationships exist anywhere in this schema (verified:
  `auth_group_permissions`, `accounts_user_groups`,
  `accounts_user_user_permissions` — the only M2M tables — are all empty and
  unused).
- Every foreign key checked above resolves with **zero orphans** (verified
  directly: every `Resource.subject_id` matches an existing `Subject.id`).

## User Migration Considerations

**This needs a decision before the next phase runs anything, not a blind
copy.**

- **Local:** 2 users. One `ADMIN` (`is_staff=True`, `is_superuser=False`,
  `is_active=True`), one `STUDENT` (`is_staff=False`, `is_active=True`).
  Both password hashes use `pbkdf2_sha256` — Django's own default hasher,
  already the first entry in `PASSWORD_HASHERS`. **No legacy bcrypt hashes
  present locally**, so there is no hasher-compatibility concern for these
  two specific accounts (the bcrypt hasher in `settings.py` exists for a
  different, older migration this project already went through — not
  relevant to what's in this database now).
- **Supabase:** 1 user — the account created via `createadmin` directly
  against Supabase after Phase 2, for accessing this deployment. This is a
  *third*, independent account, not a copy of either local user.
- **Password hashes were not read, displayed, or compared in this
  analysis** — only the hasher algorithm name (the fixed prefix before the
  first `$`) was checked, never the hash or any derived secret.
- **The real decision:** does the local `ADMIN` user need to become the
  Supabase admin (replacing or alongside the one just created), does the
  local `STUDENT` user need to exist on Supabase at all, or is starting
  Supabase with fresh accounts acceptable? This is a product decision, not
  a technical one, and this phase does not make it.
- **JWT consideration:** access/refresh tokens are signed with
  `REC_SECRET_KEY`, which is (and must remain) different between local
  development and the Supabase/production environment. No token issued
  locally is valid against Supabase regardless of whether `User` rows are
  migrated — this is why `token_blacklist_*` is excluded above. Migrating
  users means migrating their identity and stored password hash, never a
  live session.

## Recommended Migration Strategy

**Recommended: Django's own `dumpdata` / `loaddata`, scoped per-app, run
manually and reviewed before loading — not a custom ORM script, and not a
raw SQL export.**

Why this fits this schema specifically:

1. **The schema has no exotic types.** Confirmed in Phase 1's compatibility
   audit and re-confirmed here: no raw SQL, no database-generated defaults
   Django doesn't know about, one plain `JSONField` (`WaContact.context`,
   irrelevant here since it's empty). `dumpdata`/`loaddata` round-trips
   Django's own serialization format, which handles every field type this
   project actually uses without any custom mapping code.
2. **The dependency chain is a straight line** (Department → Semester →
   Subject → Resource, plus User as a side reference) **with no
   many-to-many tables in play** — `loaddata` restores foreign keys
   correctly as long as the dump is loaded in dependency order, which a
   per-app dump naturally gives if apps are loaded in the order above. No
   need for a topological-sort script.
3. **It's the built-in, reviewable option.** The output is plain JSON —
   readable before loading, diffable, and small (1,094 rows of catalogue
   data is not a bulk-data problem). A custom script would be more code to
   get wrong for no benefit at this size.
4. **It deliberately does NOT include the tables this plan says to
   exclude** — `dumpdata` is invoked per-app/per-model, so
   `token_blacklist`, `auth.permission`, `contenttypes`, and the unused M2M
   tables are simply never dumped in the first place, rather than needing
   to be filtered out after the fact.

What this rules out, and why:
- **A raw SQL export/import** — would need hand-written type mapping
  between SQLite's dynamic typing and PostgreSQL's strict typing (dates,
  booleans, and the JSON field all serialize differently), for no benefit
  over a tool that already does this correctly.
- **A custom Django ORM script** (`for obj in Model.objects.all(): ...`) —
  more code than `dumpdata`/`loaddata` for the same result, and the
  dependency-chain ordering has to be reimplemented by hand instead of
  falling out of the app-load order for free.
- **`pg_dump`/`pg_restore`** — not applicable; the source is SQLite, not
  Postgres.

## Backup Procedure

**Before any future migration runs, back up the local SQLite file — it is
never deleted or altered by this plan, but a backup costs nothing and is
the obvious first real step of the next phase:**

```bash
cd backend
copy rec_aids.sqlite3 rec_aids.sqlite3.backup-%date:~-4,4%%date:~-7,2%%date:~-4,2%
```

(PowerShell equivalent: `Copy-Item rec_aids.sqlite3
"rec_aids.sqlite3.backup-$(Get-Date -Format yyyyMMdd)"`.) SQLite is a single
file — copying it while the app isn't actively writing is a complete,
consistent backup. `.legacy-backup/` already exists in `.gitignore` as a
precedent for keeping a backup out of git; a new dated copy should follow
the same pattern (add its own entry, or place it there) rather than being
committed.

The `backend/media/` folder (the actual resource files) should be backed
up the same way — a plain recursive copy — before any future Storage
migration, for the same reason.

## Validation Plan

For a future migration phase to confirm before declaring success:

- Row counts match exactly: local vs. Supabase, per model, for every
  migrated table (the same comparison table in this document, re-run
  post-migration).
- Every `Semester.department_id`, `Subject.semester_id`, and
  `Resource.subject_id` on Supabase resolves to an existing row (the same
  zero-orphan check performed in this analysis, re-run against Supabase).
- `UniqueConstraint`s hold on Supabase exactly as they do locally — no
  duplicate `(department, semester_number)` or `(semester, course_code)`
  pairs (PostgreSQL will enforce this at load time and refuse a violating
  row, so a clean `loaddata` run is itself partial evidence; an explicit
  post-load query is still worth running).
- Spot-check the frontend against the migrated data once loaded: pick a
  department, confirm its semesters/subjects/resources render — this is
  the same "existing functionality" verification already performed against
  the (currently empty) Supabase schema in Phase 2, re-run once it's
  populated.
- Primary keys preserved (§Preserve IDs) — confirm a specific known
  `Subject.id` (e.g. `12`) still holds the same course on Supabase as it
  does locally.

## Rollback Plan

Since this plan recommends `loaddata` (an additive operation, not a
destructive one) and nothing has been migrated yet:

- **If a future migration attempt fails partway:** the safest rollback for
  this schema is to truncate just the tables that were being loaded
  (`Resource` → `Subject` → `Semester` → `Department`, deletion in reverse
  dependency order to satisfy foreign keys) via
  `Model.objects.all().delete()` for each, then re-run `loaddata` from the
  reviewed dump once the underlying problem is fixed. This only touches
  Supabase, which currently holds no real data to lose.
- **The local SQLite database is never at risk** — every step in this plan
  and the one it recommends only *reads* from SQLite (`dumpdata`) and only
  *writes* to Supabase (`loaddata`). The backup in §Backup Procedure is
  extra safety, not a dependency of the rollback.
- **If the whole approach needs abandoning:** Supabase's tables can be
  cleared with the same per-model `.delete()` calls above (or, since the
  schema itself is unaffected either way, dropping and re-`migrate`-ing is
  equally safe — the schema is reproducible from migrations at any time).

## Risks

1. **User migration is a decision, not a mechanical step** (§User Migration
   Considerations) — the highest-risk part of any future migration phase
   is proceeding without that decision being made explicitly first.
2. **Primary key preservation** (see below) needs the auto-increment
   sequence resynchronized after a `loaddata` that specifies explicit PKs,
   or PostgreSQL's `nextval()` will collide with a manually-loaded ID on
   the next natural insert. Django's `loaddata` on PostgreSQL handles this
   automatically for a full-database load; scoped/partial loads should
   verify it explicitly (`SELECT setval(...)` per sequence) rather than
   assume it.
3. **File bytes are not covered by this plan at all** — migrating
   `Resource` rows without also handling the 50 MB of actual PDFs (still
   local-disk-only, still out of scope) would leave Supabase-side metadata
   pointing at files that don't exist from wherever the app eventually
   runs. This is fine as long as the app keeps running from this same
   machine/disk in the meantime, but is a real dependency for any future
   phase that also changes *where* the app runs.
4. **The one Supabase `accounts_user` row already created** (the
   post-Phase-2 admin) needs to be explicitly reconciled with, not silently
   overwritten by, whatever the user-migration decision produces.
5. **Scale is small** (1,094 rows, 50 MB of files) — there is no
   performance/batching risk here worth engineering around.

## Next Steps

The exact migration plan to execute in the next phase, once explicitly
approved:

1. Back up `backend/rec_aids.sqlite3` and `backend/media/` (§Backup
   Procedure).
2. Get an explicit decision on user migration (§User Migration
   Considerations) — this blocks step 5 below and should happen first,
   independent of everything else.
3. From `backend/`, with `REC_DATABASE_URL` cleared (local SQLite as the
   *source*):
   ```bash
   python manage.py dumpdata academics.department --indent 2 -o /tmp/01_departments.json
   python manage.py dumpdata academics.semester --indent 2 -o /tmp/02_semesters.json
   python manage.py dumpdata academics.subject --indent 2 -o /tmp/03_subjects.json
   python manage.py dumpdata resources.resource --indent 2 -o /tmp/05_resources.json
   ```
   (User dump deliberately not included in this list yet — depends on step
   2's outcome; may be a full `accounts.user` dump, a filtered one, or
   skipped entirely in favor of manually created accounts.)
4. **Review every dump file by hand** before loading anything — this is
   the checkpoint where a mistake gets caught before it reaches Supabase.
5. With `REC_DATABASE_URL` set to the Supabase connection (target):
   ```bash
   python manage.py loaddata /tmp/01_departments.json
   python manage.py loaddata /tmp/02_semesters.json
   python manage.py loaddata /tmp/03_subjects.json
   # user step here, per the step-2 decision
   python manage.py loaddata /tmp/05_resources.json
   ```
6. Run the full §Validation Plan.
7. Only after validation passes: consider file-storage migration (a
   separate, later phase) and update `docs/all-phases-details.md` with the
   result.
